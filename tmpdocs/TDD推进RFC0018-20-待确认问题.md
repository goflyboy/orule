## D1 — SimpleTSParser 模块归属 vs GraalJS 依赖

**问题**：RFC-0018 §3.1 把 `com.orule.dsl`（含 SimpleTSParser / WhitelistPruner / FieldValidator 等 15 个类）
放在 **`packages/orule-common`**。但 §3.9 的 `TsAstParser` 依赖 GraalJS（~30 MB jar）+ TypeScript npm 包。

**冲突点**：
- orule-common 当前依赖只有 lombok / jackson / hibernate / spring-validation / slf4j / commons-codec，**无 GraalJS**
- orule-server 之前可能有 GraalJS（待核实）
- orule-runtime 当前**无 GraalJS**

**两种方案**：

### D1A — 按 RFC 把 dsl 留在 orule-common，引入 GraalJS + TypeScript（推荐）

- **优点**：与 RFC 一致；下游 orule-server / orule-runtime 直接调用 `parser.parse(...)`
- **代价**：orule-common jar 体积 +30MB；TypeScript npm 包需要 npm 资源；
  实测编译期每条规则多 100~500ms（JVM 启动 GraalJS context）
- **TDD 影响**：测试用 `@TempDir` 写一个最小 TypeScript 入口文件，CI 会下载

### D1B — 把 dsl 包拆到 `orule-server`，SimpleTS 解析在服务端走完整流程

- **优点**：orule-common 保持轻量；GraalJS 只在服务端依赖
- **代价**：与 RFC 不一致，需要修订 RFC-0018 §3.1；
  RFC-0020 沙箱如果想本地 dry-run SimpleTS，得重新依赖 dsl 包
- **TDD 影响**：测试边界清晰（GraalJS 副作用只发生在服务端）

### D1C — 在 orule-common 里只放解析骨架（不含 GraalJS），GraalJS 通过 DI 注入

- **优点**：orule-common jar 不变大；TDD 时 mock TsAstParser 即可
- **代价**：比 RFC 多一层接口；实现复杂一点
- **TDD 影响**：测试快，无外部依赖

**我的推荐**：**D1C**（最符合 TDD 节奏）或者 **D1A**（最贴近 RFC）。
考虑到 RFC 是设计文档，最终方案应当 = 实际实现位置，**D1C 是更稳妥的工程实践**。

## D2 — RFC-0020 沙箱放在 orule-runtime，但当前 pom 没 Groovy 依赖

**问题**：RFC-0020 §3.1 在 `packages/orule-runtime/src/main/java/com/orule/runtime/execution/` 下，
明确写"依赖 groovy-all (groovy.version=4.0.24)"。但运行时 pom 里**完全没有 groovy 依赖**。

**两种方案**：

### D2A — 按 RFC 在 orule-runtime/pom.xml 添加 `groovy` + `groovy-jsr223` + `groovy-test` 依赖

- **依赖坐标**：parent pom.xml 已经有 `<groovy.version>4.0.24</groovy.version>`
- **需要补**：父 pom 加 `org.codehaus.groovy:groovy-all:4.0.24` 进 dependencyManagement
- **影响**：runtime jar +5MB；首次启动慢 200ms

### D2B — 把 RFC-0020 沙箱代码挪到 orule-common

- **优点**：与 RFC-0018/0019 同模块，复用 Groovy 依赖
- **代价**：与 RFC-0020 §3.1 不符；runtime jar 反而不能直接用（得通过 common 间接）

**我的推荐**：**D2A**（按 RFC，runtime 跑沙箱，最自然）。

## D3 — RFC-0019 codegen 同模块 vs 拆模块

**问题**：RFC-0019 §3.1 把 `com.orule.dsl.codegen` 也放在 `orule-common`。
但 codeGen 涉及 Groovy 字符串拼接（与 D2 的 Groovy 依赖关联）。
如果 D1 选了 A（common 引入 GraalJS），那 D3 也得在 common 引入 Groovy。

**推荐**：与 D2 联动 —— **D1C 配 D2A**（codegen 留 common，沙箱放 runtime）。

## D4 — RFC-0020 安全测试需要的 OWASP 工具

**问题**：RFC-0020 §5.2 列出安全测试用例 14 项（System.exit / Runtime.exec / Class.forName / ProcessBuilder
等），但当前项目没有：
1. Groovy 实际环境（如果 D2A 解决了 pom，就有 Groovy）
2. OWASP fuzz 工具
3. 内存/超时压测工具（JMeter / Gatling 未引入）

**两种方案**：

### D4A — 只做 RFC §5.2 单元层安全测试 + 跳过渗透测试（推荐 MVP）

- **优点**：可达 RFC §5.2 表格中"测试可行"的那 8 项
- **代价**：不覆盖 OWASP fuzz

### D4B — 引入 JMH + 完整的 OWASP fuzz 框架

- **代价**：2 工期以上的额外工作；超出 RFC 给的 5 天工作量

**我的推荐**：**D4A**（先把 RFC 列的安全测试跑通，fuzz 二期再说）。

## D5 — RuleType 引入后 TestMetaFactory 如何构造测试夹具

**问题**：RFC-0018-bis 将 `SimpleTSParser.parse()` 入口从 `(source, DomainMeta)` 改为 `(source, RuleType)`。
现有 `TestMetaFactory.orderDiscount()` / `.simple()` 工厂方法返回 `DomainMeta`，需重构。

**推荐方案 D5A**（最符合 entity 层设计）：

在 `TestMetaFactory` 中新增 `orderDiscountRuleType()` / `simpleRuleType()` 工厂方法，
直接构造 RuleSet → RuleType → ArgumentType → ObjectType 链：

```java
public static RuleType orderDiscountRuleType() {
    // 构造 ObjectType（Customer / Order / CustomerTier）
    ObjectType customer = buildCustomer();
    ObjectType order    = buildOrder();
    ObjectType tier     = buildCustomerTier(); // kind=ENUM

    // 构造 RuleSet
    RuleSet rs = RuleSet.builder()
        .id("rs-order").code("ORDER_DISCOUNT").name("订单满减规则集")
        .objectTypes(List.of(customer, order, tier))
        .functionTypes(List.of(/* math / string / date FuntionType */))
        .build();

    // 构造 ArgumentType
    ArgumentType argCustomer = ArgumentType.builder()
        .id("arg-customer").programCode("customer")
        .objectType(customer).nullable(false).writable(false)
        .sortOrder(0).build();

    ArgumentType argOrder = ArgumentType.builder()
        .id("arg-order").programCode("order")
        .objectType(order).nullable(false).writable(true)
        .sortOrder(1).build();

    // 构造 RuleType
    RuleType rt = RuleType.builder()
        .id("rt-order-discount").code("ORDER_DISCOUNT_RULE").name("订单满减规则")
        .ruleSet(rs).validatable(true)
        .arguments(List.of(argCustomer, argOrder))
        .functionTypes(List.of(/* math / string / date FuntionType */))
        .build();

    argCustomer.setRuleType(rt);
    argOrder.setRuleType(rt);

    return rt;
}
```

**影响**：
- §5 关键测试用例（`vipDiscount_compileSucceed` 等）全部改用 `TestMetaFactory.orderDiscountRuleType()`
- `DomainMeta` 相关测试夹具降级为"历史参考"，不删除（保留 RFC-0018 修订前参考）

**备选 D5B**：保留 `DomainMeta` 工厂方法，新增 `RuleType` 工厂方法，两套并存（过渡期兼容）。

**我的推荐**：**D5A**（直接对齐 entity 层，测试最贴近实际使用场景）。
