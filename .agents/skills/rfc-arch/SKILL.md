# RFC-Arch：RFC 式渐进架构设计

## Overview

以 RFC（提案→评审→修订→定稿）的迭代节奏，结合 4+1 视图文档结构，与用户逐轮协作产出一份完整的系统架构设计说明书。

核心原则：**一次只推进一层；AI 先澄清、用户后决策；每轮结论回写文档；设计完必须对抗验证。** 用户是决策者，AI 是顾问。

## 核心方法论（精简版）

只使用以下方法，不引入其他重方法论：

| 方法 | 用途 |
|---|---|
| 4+1 视图 | 文档结构骨架：用例/逻辑/开发/部署/运行 5 个视图 |
| ADD（属性驱动设计） | 每层设计前先明确该层的质量属性（性能/可用性/安全/可维护性）作为验收标准 |
| ADR（架构决策记录） | 每个关键决策产出一页纸记录：背景/候选/决策/后果 |
| DDD（领域驱动设计） | 逻辑视图与领域模型阶段：限界上下文、聚合、领域事件 |
| RFC 式迭代 | 整体节奏：提案→评审→修订→定稿 |

推进顺序（对应 4+1 视图模板章节）：

1. 边界与目标（简介、总体设计）
2. 用例视图
3. 逻辑视图（逻辑模型、领域模型、功能模型）
4. 数据模型
5. 技术模型
6. 运行视图
7. 部署视图
8. 开发视图与质量属性落地
9. 收口：跨层一致性、ADR 汇总、风险清单

## 会话协议（四条铁律）

1. **一次只推进一层。** 每轮只讨论一个章节或一个决策点，绝不一次生成整份文档。
2. **AI 先澄清，用户后决策。** 每轮先由 AI 向用户提问（最多 10 个），用户回答后 AI 才产出设计，禁止 AI 脑补前提。
3. **每轮结论必须回写文档。** 对话是易失的，文档是唯一事实源；每轮结束把定稿写入 MD 文件并更新 ADR。
4. **设计完必须对抗验证。** 让 AI 切换对抗角色（安全/运维/数据/成本/竞对）挑毛病，挑不出毛病视为未验证。

## 工作流

### 启动协议（一次性）

执行一次以下动作，建立协作基线：

1. 让用户提供：架构模板路径（如 4+1 视图模板 MD）、项目背景、约束清单、已定决策。
2. 设定 AI 角色：首席架构顾问 + 对抗评审人，并声明协作规则（四条铁律）。
3. 输出推进计划：确认第一轮主题。

启动提示词模板见 `references/prompts.md` 的「启动协议」。

### 逐轮推进（每轮四步）

每轮固定执行以下四步：

1. **澄清**：AI 先向用户提问，把影响该层设计的前提问清楚（业务目标、约束、NFR、已有资产、冲突点）。
2. **设计**：用户拍板方向后，AI 产出该层设计——先给 2-3 个候选方案对比表，再给推荐及理由，再展开细节。
3. **验证**：AI 切换对抗评审角色，找出 3-5 个最严重问题，按严重程度排序并给修改建议。
4. **回写**：定稿写入架构文档对应章节，每个关键决策生成一条 ADR。

各轮具体提示词模板见 `references/prompts.md`。

### 收口轮

执行整体评审：

1. 跨层一致性：逻辑模块 vs 代码结构 vs 部署单元是否对齐。
2. 质量属性覆盖：每个 NFR 是否都有对应设计。
3. 未决问题清零：所有 OPEN 项是否都有责任人。
4. 风险清单：按概率×影响排序，给应对措施。
5. 输出最终版目录和修订记录。

## 对抗评审角色库

评审阶段轮换使用以下角色（每次一个或按需组合）：

| 角色 | 关注点 |
|---|---|
| 安全专家 | 攻击面、权限、加密、审计 |
| 运维专家 | 可观测性、故障恢复、RTO/RPO |
| 数据专家 | 一致性、数据质量、数据所有权 |
| 成本专家 | 生产成本、更省替代方案 |
| 竞争对手 | 方案弱点挖掘 |
| 新手开发 | 文档可理解性、能否独立开发 |

## 防止跑偏三招

1. **矛盾即打断**：AI 编造用户没说的前提时，直接指出并纠正。
2. **要求标注置信度**：让 AI 对不确定结论标注[推断]/[猜测]。
3. **以文档为准**：每轮开始要求先读文档现状再继续。
