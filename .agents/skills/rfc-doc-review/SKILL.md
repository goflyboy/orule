# RFC 文档审查

> 配套：[`.agents/skills/interactive-rfc-generation/SKILL.md`](../interactive-rfc-generation/SKILL.md) · [`.agents/skills/audit-docs/SKILL.md`](../audit-docs/SKILL.md) · [`.agents/README.md`](../../README.md)
> 与 `interactive-rfc-generation` 的关系：那边负责"生成新 RFC"；本 Skill 负责"审查并修订已存在的 RFC"。

## 0. 何时使用 / 何时不使用

**使用**：

- 用户说"审查 / 检视 / review / audit / 修改 RFC-XXXX"。
- 用户给 RFC 路径，要求 AI 自检后再决定改 / 不改。

**不使用**：

- 生成新 RFC（用 `interactive-rfc-generation`）。
- 给任意文档做系统性体检（用 `audit-docs`）。

## 1. 硬性约束

- 默认审查后直接修改 RFC 文件。
- 修改前必须先备份原 RFC，备份文件名必须包含"原文档"（如 `RFC-0011-XXX-原文档.md`）。
- 如用户明确说"不改 / 先不要改 / 只审查 / 只提意见 / 等我确认"，则只输出审查意见，不修改、不备份。
- 审查阶段不写实现代码。
- 用户在 SpecStory 里的人工输入优先级最高。
- 当前代码证据优先于 RFC 中的想象性接口。
- 事实 / 推断 / 疑问要区分清楚；没有证据时标为"需确认"。

## 2. 修改与备份规则

默认模式下，在编辑 RFC 前先复制原文档：

- 原文件：`docs/rfcs/RFC-0011-XXX.md`
- 首选备份：`docs/rfcs/RFC-0011-XXX-原文档.md`
- 如首选备份已存在，使用时间戳：`docs/rfcs/RFC-0011-XXX-原文档-20260919-111530.md`

备份完成后再修改原 RFC 文件。**不要修改备份文件**。

## 3. RFC 修订质量规则

修改 RFC 时，必须参考 `interactive-rfc-generation/SKILL.md` §4 RFC 质量门与本目录的 `REVIEW_PROMPT.md`。重点检查：

- **模块归属**必须明确指向 `orule-common / orule-rule-execution-service / orule-server / 跨模块` 之一；不允许出现 `cruleengine / crulemgr / 顶层` 等本仓库不存在的命名。
- **复用优先**清单完整：现有入口 / helper / 测试基类 / DSL / 不新增 / 可推导字段。
- **分层边界**：区分产品 / 模型声明、生成、运行时求解、校验、测试辅助。
- **依赖方向**：对照 [ARCHITECTURE.md §0 依赖方向](../../../ARCHITECTURE.md)，禁止反向依赖。
- **接口矩阵**：列出受影响入口，每个入口有验收用例或明确"不在范围内"。
- **测试简洁性**：测试样例只表达本 RFC 关注点，不写未使用字段；优先复用项目已有测试基类与 helper。
- **诊断语义**：新增校验接口时，说明 boolean 结果 / 错误详情 / violated rule code 如何返回和测试。
- **进度标记**：顶部状态按项目习惯：`草案（Draft）` / `评审中（Review）` / `已批准（Approved）` / `已实现（Implemented）`。

## 4. 输入发现

### 4.1 正式 RFC 文档

用户给定路径优先，否则：

```powershell
rg --files docs/rfcs | rg "RFC-.*\.md$"
```

阅读 RFC 时重点看：

- 动机 / 范围 / 非目标是否明确。
- 方案、接口、数据结构、示例代码是否互相对应。
- 验收标准是否可执行、可观察，覆盖正向 / 反向 / 边界。
- 实现计划是否能映射到当前代码位置。

### 4.2 SpecStory 沟通记录

```powershell
rg "RFC-XXXX|<关键词>" .specstory/history
```

角色标记：

- `_**User`：人工输入，重点阅读。
- `_**Agent`：模型输出，降权处理。
- `<tool-use>` / `<think>`：工具日志与推理段，跳过。

处理规则：

- 先抽取所有人工输入片段。
- 对人工输入做小表格：原始诉求 / 修正点 / 设计含义 / 当前 RFC 是否落实。
- 模型输出与用户输入冲突时，以用户输入为准。

### 4.3 现有代码

```powershell
rg "<类名|方法名>" packages
```

重点验证：

- RFC 提到的入口 / 类名 / 方法名 / 字段名 / 枚举值是否真实存在。
- 是否有 builder / parser / validator / executor / annotation / serializer 可复用。
- 是否有相似测试与测试基类；不要轻易接受 RFC 中新增测试 helper 的设计。
- 新功能应该放在哪个模块边界，是否绕开已有架构。
- RFC 是否遗漏兼容性 / 迁移 / 诊断信息 / 失败行为 / 回归测试。

## 5. 审查流程（四步）

### 第一步：正式文档审查

按 §3 质量规则逐条检查。

### 第二步：人工修正复核

从 SpecStory `_**User` 抽取修正点，逐条判断：

- `已落实` / `部分落实` / `未落实` / `需确认`。

复核重点是"用户为什么要纠偏"，不是复述聊天。

### 第三步：代码对齐审查

按 §4.3 用当前代码校验 RFC 是否可实现、是否符合本项目习惯。

### 第四步：备份并修订文档

默认模式下：

1. 按 §2 创建原文档备份。
2. 修改原 RFC 文件，**不修改备份**。
3. 修改内容要能追溯到正式 RFC / SpecStory 人工输入 / 代码证据。
4. 不要把"需确认"的推断写进 RFC 正文；只在最终输出里列为待确认。
5. 修改后重新阅读相关章节，确认没有格式断裂 / 重复章节 / 自相矛盾。

如用户明确要求不改，跳过本步，只输出审查意见。

## 6. 输出格式

### 默认修改模式

```text
结论：已完成审查并直接修订 RFC；原文档已备份到 <备份路径>；主要修改解决了哪些风险；仍有哪些问题需要用户确认。
```

```markdown
## 已修改
- 问题标题
  - 依据：RFC 章节 / SpecStory 人工输入片段 / 代码位置
  - 修改：说明已经改了 RFC 哪些内容

## 原文档备份
- <备份路径>

## SpecStory 人工修正复核
- 修正点：
  - 状态：已落实/部分落实/未落实/需确认
  - 处理：

## 代码对齐检查
- 已对齐：
- 已修正：
- 仍需补充验证：

## 待用户确认
- Q1 ...
```

### 只审查不改模式

```text
结论：当前 RFC 是否可以进入修改/实现；主要风险是什么；是否需要先等用户确认。
```

```markdown
## 必须修改
- [高/中/低] 问题标题
  - 依据 / 问题 / 建议

## 建议修改
- ...

## SpecStory 人工修正复核
- 修正点：
  - 状态：已落实/部分落实/未落实/需确认
  - 复核意见：

## 代码对齐检查
- 已对齐：
- 不一致：
- 需要补充验证：

## 待用户确认
- Q1 ...
```

## 7. 证据规则

- 本地代码证据尽量带文件路径 + 行号。
- SpecStory 证据要说明是"人工输入"还是"模型输出"。
- 只是根据有限文件推断时，明确写"推断"。
- 不要因为措辞风格提出修改；重点审查设计正确性 / 实现可行性 / 测试完整性 / 用户修正是否被落实。

## 8. 用户明确要求不改时

按 §5 第四步跳过；输出 §6 只审查不改格式。等待用户确认后：

1. 复述将应用哪些审查意见。
2. 按 §2 备份原文档。
3. 只修改已确认的问题。
4. 尽量保留 RFC 原结构与术语。
5. 修改后重新阅读相关章节，并说明具体改了什么。

如用户否定某条意见，将该否定视为本轮后续工作的项目偏好。
