# RFC 评审检查清单

> 配套：`.agents/skills/interactive-rfc-generation/SKILL.md`
> 调用方：AI Agent 在 RFC 起草完成后、提交给用户审之前自评；或人类 Reviewer 在 PR 中评审时使用。

---

## 0. 评审维度（与 SKILL.md §4 RFC 质量门一一对应）

| 维度 | 对应 SKILL.md §4 检查项 | 本文件章节 |
|------|------------------------|-----------|
| 完整性 | "RFC 包含具体可执行的验收命令" | §1 |
| 模块归属 | "RFC 明确说明属于哪个模块" | §2 |
| 复用优先 | "测试示例优先使用项目已有测试基类与 helper" | §3 |
| 合规性 | "没有引入反向依赖 / 没有引入与 AGENTS.md 冲突的写法" | §4 |
| 可验证性 | "RFC 包含具体可执行的验收命令和模块专属测试" | §5 |

---

## 1. 完整性检查

- [ ] 包含摘要 / 动机 / 设计方案 / 复用优先 / 验收准则 / 实现计划 / 参考资料
- [ ] 摘要 1-3 句话说清问题与方案
- [ ] 动机部分包含具体问题场景与示例
- [ ] 设计方案覆盖所有边界情况
- [ ] 验收准则包含具体可执行的测试用例
- [ ] 参考资料链接全部可解析（起草后跑一次 audit-docs 自检）

## 2. 模块归属检查

- [ ] 显式写出"模块归属"段（按 TEMPLATE.md §2）
- [ ] 范围限定在 `orule-common / orule-rule-execution-service / orule-server / 跨模块` 之一
- [ ] 若为"跨模块"，明确两个模块各自的归属与依赖方向
- [ ] 没有使用"顶层"等 ARCHITECTURE.md 已废用语
- [ ] 依赖方向合规（对照 ARCHITECTURE.md §0）

## 3. 复用优先检查

- [ ] 列出既有入口点 / helper / 测试基类
- [ ] 明确"不新增"的项
- [ ] 可推导字段不要求用户重复填写

## 4. 合规性检查

- [ ] 没有引入反向依赖
- [ ] 没有 inline 限定符（AGENTS.md §STY-J001）
- [ ] 测试类 `public class`（AGENTS.md §STY-J002）
- [ ] 没有把 `org.junit.Test`、`org.junit.jupiter.api.Test` 等混用

## 5. 可验证性检查

- [ ] 验收命令具体到 `mvn -pl <module> -am test -Dtest=<TestClass>#<testMethod>`
- [ ] 边界条件表格存在
- [ ] 回归测试项存在
- [ ] 模块专属测试路径正确（参考 TEMPLATE.md §10）

---

## 6. 评审输出格式

```markdown
## RFC-XXXX 评审报告

**评审日期**：YYYY-MM-DD
**评审者**：AI / <name>

### 整体评价

[优秀 / 良好 / 需要改进]

### 严重问题（🔴）

1. [问题描述]
   - 位置：[章节]
   - 修复建议：[具体改动]

### 建议改进（🟡）

1. [改进建议]

### 一致性 / 可验证性 / 合规性 备注

- ...

### 结论

[建议批准 / 需要修改后重新评审 / 建议拆分 RFC]
```

---

## 7. 评审执行步骤

1. 读取 RFC 文档全文。
2. 按 §1–§5 维度逐项检查。
3. 起草 §6 格式的评审报告。
4. 输出到对话中，或保存到 `tempdocs/audit-<日期>/RFC-XXXX-review.md`。

---

## 8. 评审注意事项

- 保持客观，基于文档内容评价，不引入未在 RFC 中提到的假设。
- 重点关注可执行性和测试覆盖。
- 指出问题时同时提供修复建议。
- 确保与项目整体设计保持一致（[AGENTS.md](../../../AGENTS.md) · [ARCHITECTURE.md](../../../ARCHITECTURE.md)）。
