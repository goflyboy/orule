# ADR-007：四进程架构（管控 / 执行 / LLM / 共享）

> 状态：已通过
> 日期：2026-09-11
> 决策者：架构组
> 相关：01-边界与目标、03-逻辑视图、04-数据模型、05-技术模型

---

## 决策

将 orule 后端拆分为 **4 个独立进程**：

| 进程 | 职责 | 端口 | Spring Boot Application |
|------|------|------|------------------------|
| `orule-server` | 管控面：元数据/规则/制品管理 + MCP（进程内）+ SimpleTS 编译 | 8080 | `OruleServerApplication` |
| `orule-runtime` | 执行面：Groovy 沙箱执行 + ExecutionLog | 8081 | `OruleRuntimeApplication` |
| `orule-llm` | LLM 服务：OpenAI/Anthropic 后端原生调用 | 8082 | `OruleLlmApplication` |
| `orule-common` | 共享库：DTO / Entity（被前 3 个依赖） | - | 仅 JAR，无启动类 |

---

## 原因

1. **管控 / 执行负载特征不同**
   - `orule-server`：IO 密集（数据库读写、文件 IO）
   - `orule-runtime`：CPU 密集 + 内存敏感（Groovy 类加载）
   - 部署在一起会出现资源竞争，独立服务可独立扩缩容

2. **执行隔离需求**
   - orule-runtime 需要 groovy-sandbox 安全沙箱
   - 与管控代码物理隔离，即使沙箱被绕过也不影响元数据

3. **LLM 服务独立**
   - LLM API Key 绝不出服务器
   - 未来可被其他业务系统复用（不限于 orule-web）
   - 控制 LLM 调用成本 / 限流 / 监控

4. **未来扩展性**
   - LLM 服务部署在内网（数据不出内网）
   - Runtime 可部署多个实例（按规则集分组）
   - Server 可水平扩展（无状态）

---

## 备选方案

### 备选 1：单进程（最初方案）
- 优点：部署简单
- 缺点：资源竞争、扩缩容受限、沙箱隔离差

### 备选 2：二进程（server + runtime）
- LLM 与 server 同进程（不开源 SDK）
- 缺点：LLM Key 安全风险、LLM 调用影响 server 性能

### 备选 3：四进程（本方案）
- **采纳**：最清晰的职责划分，最高安全性

---

## 后果

### 复杂度增加
- 服务间通信：REST + Spring Cloud OpenFeign
- 部署复杂度：Docker Compose 需要启动 4 个服务 + 2 个前端 + DB
- 日志聚合：需要 ELK / Loki 跨服务追踪

### 性能影响
- 服务间调用延迟：+5ms（HTTP 内部调用）
- 数据一致性：共用数据库 + JPA（事务仍可保证）

### 收益
- 沙箱隔离：执行错误不会污染管控
- 扩缩容：runtime 可独立扩 10 实例，server 只需 2 实例
- 安全：LLM Key 不外露
- 可维护：每个服务 1 个 PR，职责清晰

## 通信矩阵

| 调用方 | 被调用方 | 协议 | 备注 |
|--------|----------|------|------|
| `orule-web` → `orule-server` | REST | HTTP | CRUD / 编译 / 打包 |
| `orule-web` → `orule-llm-studio` | iframe | - | 嵌入 UI |
| `orule-llm-studio` → `orule-llm` | REST | HTTP | chat / 转换 |
| `orule-runtime` → `orule-server` | REST + Spring Cloud Feign | HTTP | 拉取 RuleArtifact |
| `orule-mcp-server` → `orule-server` | REST | HTTP | MCP 透传 |
| `orule-llm` → OpenAI / Anthropic | HTTPS | - | LLM API |
