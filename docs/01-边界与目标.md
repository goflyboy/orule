# 01 · 边界与目标

> **第 1 轮定稿** · 2026-09-10

---

## 1.1 系统愿景

**orule**（"open rule"）是面向 AI 消费场景的规则底座。

核心承诺：**一种语义，多种表现形态**。

- 同一条规则可以被业务人员（自然语言/表格/图形）查看、可以被开发者（TS/Java/Python）开发、可以被 LLM Agent 理解、可以被不同执行引擎（Groovy、cruleengine、可扩展求解器）执行。
- 表示是**第一性**的，执行是**可插拔**的。

> ⚠️ 此为对传统规则的「表示-执行绑定」结构的反转。详见调研报告 §问题二。[推断 置信度：高]

---

## 1.2 项目背景

| 维度 | 现状 | orule 的应对 |
|------|------|------------|
| 场景脱节 | 90% 业务规则是 SaaS/流程的"扩展机制型"，不需要重型推理引擎 | 默认提供宿主型轻量执行器，求解器为可选 |
| 表示-执行绑定 | 传统 DSL（DRL）绑定单一引擎，难以被 AI 消费 | TS-AST 作为通用中间态语义层；表示/执行解耦 |
| AI 幻觉 | LLM 是概率系统，不能做裁判 | 规则作为确定性内核，Agent 决策必经规则校验 |

---

## 1.3 核心定位与差异化

| 维度 | orule 的主张 |
|------|------------|
| **服务对象** | 早期客户 POC（金融/工业/政企中等复杂度规则场景） |
| **核心价值** | 让 AI Agent 接入规则系统，提升准确率与可解释性 |
| **核心特性** | 多形态展示 + 多引擎执行 + MCP 协议（与 Agent 集成） |
| **架构第一原则** | 表示优先、执行可插拔、Agent 易集成 |

---

## 1.4 MVP 范围（3 周交付）

> **决策**：3 周内交付完整链路，**不做任何功能裁剪**。cruleengine 适配、本地-云端双端 Skill、MCP 全部进入 MVP。

### 1.4.1 必须做（🔴）

| 模块 | MVP 必须做 | 验收口径 |
|------|-----------|----------|
| **元数据管理** | 领域对象元数据 CRUD + 函数库配置 + 规则形态配置（1 种） | 一个领域配置跑通 |
| **规则管理** | 规则 + 规则集 CRUD + 版本管理 + 审计字段 + 轻量后台 | 后台可增删改查、可看版本 |
| **展现态** | 自然语言形态 + 表格形态 + TS-AST 中间态 | 三种可查看、可切换 |
| **转换器** | 语法树转换器（TS-AST ↔ NL、TS-AST ↔ Table） + 1 个 LLM 转换器（NL→TS-AST） | 一条规则可在三形态无损切换 |
| **执行引擎** | Groovy 轻量执行器 + cruleengine 适配器（≥1 领域跑通） + 执行日志接口 + 持久化 | 一条规则在两种引擎均可执行并记录 |
| **自然语言 Skill** | 实体识别 Skill + 标准化规则生成 Skill + 多形态生成 Skill | 客户输入自然语言出可执行规则 |
| **数据库** | MySQL + PostgreSQL + H2 三 profile | 切换 profile 不需改代码 |
| **MCP Server** | rule_create_from_nl、rule_list、rule_execute、rule_get 四类工具 | Agent 可调用全部工具 |
| **本地-云端回路** | 本地 Skill 安装包（最小化）+ local server + 通过 MCP 回传 server | 本地生成规则可保存到 server |

### 1.4.2 留待扩展（🟡）

- 审批流 / champion-challenger
- 知识图谱集成
- OR-Tools/Gurobi 等分离式求解器
- 跨语言 SDK（Java/Python/Go）
- 自定义图形化拖拽插件 UI 框架

### 1.4.3 不做清单（MVP 明确不做）

- 多租户
- SAML/OIDC SSO（MVP 用基础 JWT 即可）
- 完整的 Agent SDK（先做 MCP 工具集）

## 1.5 非功能性目标

> 决策：**MVP 阶段先聚焦功能完整性，NFR 仅做最小兜底**，深度安全/性能/可用性需求作为遗留问题进入第二期。

### 1.5.1 兜底 NFR（必须满足）

| 维度 | MVP 兜底目标 |
|------|------------|
| **可扩展性** | 展现态插件、执行引擎、转换器、Skill 都按 SPI/插件加载机制实现。第三方基于 demo 改即可接入。 |
| **部署简单** | Docker Compose 一键起；K8s Helm 模板预留。`docker compose up` 5 分钟内可用。 |
| **混合部署** | server（云端）+ local agent（桌面）双端 Skill 跑通。 |
| **可解释** | 每次执行都输出决策路径（触发规则、条件、结论、耗时）。 |
| **数据库无关** | Flyway/Liquibase 迁移 + ORM。MySQL→PostgreSQL 不需改代码。 |
| **基础安全** | RBAC（管理/查看/执行 三角色）；执行日志 append-only；JWT 鉴权。 |

### 1.5.2 遗留 NFR（第二期处理）

- 性能基准（P99、单规则并发）
- 完整可观测性（metrics/tracing）
- 多租户隔离
- SAML/OIDC SSO
- 高级合规与审计

## 1.7 时间表（3 周硬挤版）

> ⚠️ **风险标注**：3 周内完成"NL→TS-AST→双引擎→3 Skill→MCP→本地云端回路"是激进排期。建议至少 2 人 W2 起全栈并行。

| 周次 | 交付物 | 关键里程碑 |
|------|--------|-----------|
| **W1** | 数据模型 + 后端骨架 + DB 三 profile + 元数据/规则管理 CRUD | 后台可建规则（任意形态）、数据库可切换 |
| **W2** | TS-AST 中间态 + 语法树转换器（NL/Table） + Groovy 执行器 + cruleengine 适配器 | 一条规则可在两形态切换 + 双引擎执行 |
| **W3** | 3 个 Skill + LLM 转换器 + MCP Server + 本地 Skill 安装包 + 联调 + 客户演示 | 端到端"自然语言输入 → 决策结果" + Agent 通过 MCP 调用 |
