## 8.0 本轮核心内容

开发视图描述系统对**开发者**的可见性，包括：

1. **仓库结构**：monorepo / 多 repo 策略、目录组织
2. **构建工具链**：Maven / Node / pnpm / Electron 构建器
3. **代码规范**：命名约定、风格检查、提交规范
4. **本地开发环境**：JDK / Node / 工具链版本、IDE 配置
5. **测试策略**：单元 / 集成 / E2E / 性能
6. **持续集成**：GitHub Actions / GitLab CI
7. **发布流程**：版本号、变更日志、制品发布
8. **开发护栏**：分支策略、PR 审查、保护规则

> 本章面向**开发工程师**，服务于"快速上手 + 稳定协作"。

## 8.3 代码规范

### 8.3.1 命名约定

#### Java / Kotlin

| 类型 | 命名风格 | 示例 |
|------|----------|------|
| 类 | PascalCase | `RuleService`, `ArtifactStorage` |
| 接口 | PascalCase | `EnginePlugin`, `PresenterPlugin` |
| 方法 | camelCase | `loadRule()`, `executeRule()` |
| 变量 | camelCase | `ruleVersion`, `concurrency` |
| 常量 | UPPER_SNAKE | `MAX_CONCURRENCY`, `DEFAULT_TIMEOUT_MS` |
| 包名 | 小写 | `com.orule.server`, `com.orule.runtime` |
| 测试类 | `<被测类>Test` | `RuleServiceTest` |

#### TypeScript / React

| 类型 | 命名风格 | 示例 |
|------|----------|------|
| 组件 | PascalCase | `RuleEditor.tsx`, `MetadataForm.tsx` |
| Hook | useXxx | `useRule`, `useExecutor` |
| 函数 | camelCase | `loadRule()`, `formatDate()` |
| 变量 | camelCase | `ruleVersion` |
| 常量 | UPPER_SNAKE | `API_BASE_URL` |
| 类型 / 接口 | PascalCase | `RuleVersion`, `ArtifactStorage` |
| 枚举 | PascalCase | `EngineType.GROOVY` |

#### 数据库

| 类型 | 命名风格 | 示例 |
|------|----------|------|
| 表名 | snake_case 单数 | `rule_set`, `rule_version`, `rule_artifact` |
| 列名 | snake_case | `rule_set_id`, `created_at`, `owner_code` |
| 主键 | `id` | `id VARCHAR(36)` |
| 外键 | `{被引用表}_id` | `rule_set_id` |
| 索引 | `idx_{表名}_{列名}` | `idx_rule_set_domain_id` |
| 唯一索引 | `uk_{表名}_{列名}` | `uk_rule_version_set_code` |
| 时间戳 | `{动作}_at` | `created_at`, `updated_at` |

### 8.3.3 Git 提交规范（Conventional Commits）

```
<type>(<scope>): <subject>

<body>

<footer>
```

#### type 类型

| type | 用途 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(server): 新增 RuleVersion REST API` |
| `fix` | Bug 修复 | `fix(runtime): 修复沙箱白名单未生效问题` |
| `refactor` | 重构（无功能变化） | `refactor(server): 抽取 ArtifactStorage 接口` |
| `perf` | 性能优化 | `perf(runtime): Groovy 编译缓存命中率提升至 90%` |
| `test` | 测试 | `test(server): 补充 RuleService 单元测试` |

| `chore` | 构建/CI/工具 | `chore(ci): 升级 GitHub Actions 到 v4` |
| `revert` | 回滚 | `revert: feat(server): 新增 xxx` |

### 8.4.3 一键启动脚本

```bash
#!/bin/bash
# scripts/dev-start.sh
# 一键启动全部服务（开发模式）

set -e

echo "🚀 启动 orule 本地一体化开发环境..."

# 1. 启动 MySQL（如果用 H2 则跳过）
if command -v docker &> /dev/null && [ ! "$(docker ps -q -f name=orule-mysql)" ]; then
    echo "🐳 启动 MySQL..."
    docker run -d --name orule-mysql -p 3306:3306 \
        -e MYSQL_ROOT_PASSWORD=orule_root \
        -e MYSQL_DATABASE=orule \
        mysql:8.0
    sleep 5
fi

# 2. 启动 orule-server
echo "🟢 启动 orule-server（端口 8080）..."
cd packages/orule-server
mvn spring-boot:run &
SERVER_PID=$!
cd ../..

# 3. 启动 orule-runtime
echo "🟢 启动 orule-runtime（端口 8081）..."
cd packages/orule-runtime
mvn spring-boot:run &
RUNTIME_PID=$!
cd ../..

# 4. 启动 orule-web
echo "🟢 启动 orule-web（端口 5173）..."
cd orule-web
pnpm dev &
WEB_PID=$!
cd ..

# 5. 启动 orule-llm-studio
echo "🟢 启动 orule-llm-studio..."
cd orule-llm-studio
pnpm dev &
LMS_PID=$!
cd ..

echo ""
echo "✅ 全部服务已启动！"
echo ""
echo "  📘 orule-web:        http://localhost:5173"
echo "  🔧 orule-server:     http://localhost:8080"
echo "  ⚡ orule-runtime:    http://localhost:8081"
echo "  🖥️  orule-llm-studio: http://localhost:5174"
echo ""
echo "进程 PID: server=$SERVER_PID, runtime=$RUNTIME_PID, web=$WEB_PID, lms=$LMS_PID"
echo "按 Ctrl+C 停止全部服务..."

# 等待信号
trap "kill $SERVER_PID $RUNTIME_PID $WEB_PID $LMS_PID 2>/dev/null" EXIT
wait
```

```java
@ExtendWith(MockitoExtension.class)
class RuleServiceTest {

    @Mock private RuleRepository ruleRepository;

    @Test
    @DisplayName("创建 Rule 时应同时创建第一个 RuleVersion（MAINTENANCE）")

        when(ruleRepository.save(any())).thenAnswer(inv -> inv.getArgument(0));

        // when
        Rule rule = ruleService.createRule("ORDER_DISCOUNT", "VIP 满减", "vip.discount");

        // then
        assertThat(rule.getVersions()).hasSize(1);
        assertThat(rule.getVersions().get(0).getStatus())
            .isEqualTo(RuleStatus.MAINTENANCE);
    }
}
```

### 8.5.4 关键测试用例（必须保证）

| 模块 | 必须覆盖 |
|------|----------|
| `SimpleTSParser` | 白名单剪枝 + 字段校验 + 错误行号 |
| `GroovyCodeGen` | 典型规则 + 边界条件 + 编译失败回退 |
| `GroovySandboxExecutor` | 危险 API 拦截 + 超时 + 内存限制 |
| `ArtifactStorage` | upload/download/delete + 路径穿越防护 |
| `BatchExecutionService` | 并发度 1/N/-1 + 失败容忍 |
| `RuleVersion` | 状态机迁移合法性（MAINTENANCE → PUBLISHED → RETIRED） |
| `TraceIdFilter` | 注入 / 透传 / 缺失生成 UUID |

### 8.7.1 版本号（SemVer）


后缀：

- `-RC.1`：候选发布（如 `1.1.0-RC.1`）

### 8.7.2 发布流程

```bash
# 1. 在 develop 分支合并 feature
git checkout develop
git merge --no-ff feature/RFC-0010-rule-version

# 2. 升级版本号
mvn versions:set -DnewVersion=1.1.0
# 同时修改 orule-web/package.json / orule-llm-studio/package.json

# 3. 生成变更日志
./scripts/generate-changelog.sh 1.0.0..1.1.0 > CHANGELOG.md

# 4. 提交 PR 到 main 分支
git checkout main
git merge --no-ff develop
git push origin main

# 5. 打 tag
git tag -a v1.1.0 -m "Release 1.1.0"
git push origin v1.1.0

# 6. GitHub Actions 自动触发 release workflow
# - 构建所有 JAR / 前端 / Electron
# - 推送 Docker 镜像（ghcr.io/orule/server:1.1.0 等）
# - 发布 GitHub Release（含 changelog 和制品）
```

## 8.8 分支策略（Git Flow 简化版）

### 8.8.1 分支模型

```
main (生产)
  │
  ├── develop (集成分支)
  │     │
  │     ├── feature/RFC-XXXX-xxx (功能分支)
  │     ├── feature/RFC-YYYY-yyy
  │     └── fix/bug-description (Bug 修复)
  │
  └── release/1.1.0 (发布分支)
        │
        └── hotfix/critical-bug (紧急修复)
```

### 8.8.2 分支保护规则

| 分支 | 保护规则 |
|------|----------|
| **main** | 禁止直接 push；必须 PR + 至少 1 Approve + CI 全过 |
| **develop** | 禁止直接 push；必须 PR + 至少 1 Approve + CI 全过 |
| **feature/*** | 可直接 push；Squash Merge 到 develop |
| **release/*** | 只接受 hotfix；CI 全过 |
| **hotfix/*** | 紧急流程；可跳过 Code Review 但 CI 必须过 |

### 8.8.3 提交规范

- 单一职责：一个 PR 一个特性/修复
- Squash Merge：feature 分支合并到 develop 时 squash
- 签名提交：推荐 GPG 签名（main 分支强制）
- 提交粒度：每个 commit 应该可独立编译（可选，但推荐）

## 8.9 开发护栏

### 8.9.1 文档同步

> **强约束**：任何架构级变更必须先有 ADR，PR 必须包含文档更新。

| 改动类型 | 必须更新的文档 |
|----------|----------------|
| 新增模块 / 包 | `03-逻辑视图.md` + ADR |
| 新增/修改 API | `03-逻辑视图.md` §3.5 |
| 新增/修改数据库表 | `04-数据模型.md` + Flyway migration |
| 新增/修改执行流程 | `06-运行视图.md` |
| 新增/修改部署形态 | `07-部署视图.md` |
| 重大技术决策 | 新增 ADR |

### 8.9.2 依赖管理

```xml
<!-- pom.xml 严禁做法 -->
❌ 不锁定版本：<dependency><artifactId>xxx</artifactId></dependency>
❌ 不声明 scope：默认 compile
❌ 引入传递依赖的隐式 API

✅ 推荐做法
<!-- 1. 所有版本号在 <properties> 集中管理 -->
<properties>
  <spring-boot.version>3.3.4</spring-boot.version>
</properties>

<!-- 2. 使用 BOM 统一管理 -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>${spring-boot.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<!-- 3. 显式声明每个依赖的 scope -->
<dependency>
  <groupId>com.google.guava</groupId>
  <artifactId>guava</artifactId>
  <version>33.3.1-jre</version>
  <scope>compile</scope>
</dependency>
```

### 8.9.3 安全护栏

- **依赖漏洞扫描**：GitHub Dependabot 自动检测，每周 PR
- **密钥管理**：
  - ❌ 严禁把密钥提交到 Git
  - ✅ 本地开发用 `application-local.yml`（git 忽略）
  - ✅ 生产用环境变量 / K8s Secret / Vault
- **沙箱白名单**：Groovy 沙箱必须配置 `ALLOWED_METHODS` / `ALLOWED_CLASSES`（参考 `06-运行视图 §6.3.2`）
- **SQL 注入防护**：仅使用 JPA / MyBatis 参数化查询，严禁字符串拼接

### 8.9.4 性能护栏

- **JVM 启动时间**：orule-server < 30 秒（冷启动）
- **API 响应时间**：P95 < 200ms（普通 API）；< 2s（编译 API）
- **数据库慢查询**：> 1s 的查询记录到慢日志
- **Groovy 执行**：单条规则执行 < 30s（沙箱超时）
- **批量子任务**：单批不超过 100 条规则（防止线程池爆炸）

### 8.9.5 兼容性护栏

- **API 向后兼容**：新增字段可以，删除/重命名字段必须走 `deprecate → 通知 → 下版本删除` 三步
- **数据库 schema 兼容**：新增列可，删除/重命名列必须先 `deprecate` 阶段
- **ArtifactStorage 实现**：实现接口后必须通过集成测试 `ArtifactStorageContractTest`
