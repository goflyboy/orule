# RFC-0045: 元数据驱动的执行器领域类型注入（让 ObjectType 元数据真正连到 Groovy 沙箱）

> **状态**：DRAFT · **优先级**：P1 · **预计工作量**：2.0d（v2 record + 执行器契约 + 通用 prefix 构造器 + crulemgr 端点 + RuleType 接线 + 反序列化 + 测试替换 + v0.3 清理）
> **关联 RFC**：[RFC-0040 规则执行服务](RFC-0040-规则执行服务.md)、[RFC-0042 系统测试框架](RFC-0042-系统测试框架.md)、[RFC-0043 嵌套对象 / List / Map 上下文绑定](RFC-0043-嵌套对象List与Map上下文绑定.md)、[RFC-0044 SimpleTS 与 Type 系统配套](RFC-0044-SimpleTS与Type系统配套-嵌套对象ListMap上下文绑定.md)、[RFC-0015 元数据域 CRUD API](RFC-0015-元数据域CRUD-API.md)（SUPERSEDED）、[RFC-0032 ObjectType 枚举化与 Type 系统简化](RFC-0032-ObjectType枚举化与Type系统简化.md)、[RFC-0033 元数据管理（2）— RuleSetType 与 RuleType](RFC-0033-元数据管理2-RuleSetType与RuleType.md)
>
> **v0.2 拍板（用户 2026-09-18）**：
> 1. 范围粒度：**本 RFC 一次替换** `DomainTypePrefix.CUSTOMER_ORDER`；旧的 `@Deprecated` 路径在 v0.3 提交删除。
> 2. 元数据版本化：**升级到 `RuleMetadataResponseV2`**（破坏性），controller / Feign 同步切换；不再保留 v1 record。
> 3. 上游端点：**crulemgr 在本 RFC 同期落地** `GET /api/v1/object-types/by-program-code?domainCode=&programCode=`；执行器直接消费。
> 4. hydrate 深度：**仅递归 hydrate 顶层 object slot**，list/map slot 内层不再 hydrate；与 RFC-0043 §4.3 写回语义一致。
>
> **v0.1 范围**：当前 `DomainTypePrefix.CUSTOMER_ORDER` 把 `enum CustomerTier` + `class Customer` + `class Order` 字面量写死在 Java 文本块里；`ContextHydrator` 又把 customer/order 顶层 slot、字段集合、`tier` 字符串特判、再到 dehydrate 的 simpleName 特判全列死。结果是每动一次 RuleType / ObjectType / AttributeType 元数据就要改执行器源码，违反 RFC-0033 §4.2 "RuleSetType/RuleType 元数据是 SimpleTS 编译入口"。本 RFC 把"领域类型文本生成"从执行器里拽出来，挂在元数据 API 之上，并加 `RuleMetadataResponseV2` 接线。

## 1. 摘要

把"领域 class/enum 文本"从执行器里的字面量抽出来，**以 RuleType 为中心**：

```text
RuleType.arguments[*].objectTypeCode
       └─→ GET /api/v1/object-types/by-program-code?domainCode=…&programCode=…
              └─→ ObjectType (kind=CLASS|ENUM) + AttributeType*
                     └─→ DomainTypePrefixGenerator.render(objectTypes)
                            └─→ "enum X {…}\nclass X { … }\n…"
                                   └─→ GroovyClassCache.getOrCompile
                                          └─→ Binding/Hydrate 通用化
```

同步锁定三件事：

1. `RuleMetadataResponseV2`（**v1 record 升 v2 破坏性**）：`RuleMetadataResponse` 退役，由 `RuleMetadataResponseV2` 替代；新增 `domainCode` + `objectTypeCodes[]`；`extra` 字段保留兼容窗口 1 sprint。
2. `crulemgr` 同期补端点 `GET /api/v1/object-types/by-program-code?domainCode=&programCode=`（详见 §4.4），执行器直接消费，不走本地 mock。
3. 执行器侧：
   - 删除 `DomainTypePrefix.CUSTOMER_ORDER` 这个字面量；改为 `DomainTypePrefixGenerator.render(List<ResolvedObjectType>)`，按 `kind=ENUM` 优先、再按依赖顺序排 `kind=CLASS`。
   - `ContextHydrator` 通用化：仅递归 hydrate **顶层 object slot**，list/map 内层不 hydrate；任何 `attribute.objectTypeCode == class-KIND=ENUM` 走 enum 转换，不再 `tier` 特判。
   - `dehydrateValue` 用反射读 getter 通用化，不再 simpleName 特判。

验收：[COMPUTED, 置信度 HIGH]

- `ComplexServiceFrameworkedSystemTest` 改为不写 prefix，源文本只剩规则体；metadata fixture 把 Customer/Order 描述出来；测试代码继续是「按 RFC-0043 的场景 A0/A1/B/C」。
- 新增 `DomainTypePrefixGeneratorTest` 与 `MetadataDrivenPrefixSystemTest`（新文件）。
- v0.2 提交删除 `DomainTypePrefix.CUSTOMER_ORDER` 字面量与 `apply(...)` 静态方法；v0.3 提交删除整个壳类。

## 4. 详细设计

### 4.1 总体数据流

```
RuleExecutionController.execute(request)
    └─→ RuleExecutionApplicationService.execute(request)
            ├─ 1. ruleMgmt.getRuleMetadata(ruleCode, …)
            │      → RuleMetadataResponse { …, objectTypeCodes }
            │
            ├─ 2. for code in meta.objectTypeCodes:
            │        ruleMgmt.getObjectTypeWithAttributes(code, …)  // 二次 Feign
            │      → List<ResolvedObjectType>
            │
            ├─ 3. ExecutionInput = new ExecutionInput(
            │      meta.executorType(),
            │      meta.sourceCode(),
            │      ctx,
            │      metadata,
            │      resolvedObjectTypes)        // ← 新字段
            │
            └─ 4. executorService.execute(executorType, input)
                    └─→ JavaSourceExecutor.execute(input)
                            ├─ a. prefix = DomainTypePrefixGenerator.render(input.resolvedObjectTypes())
                            ├─ b. body = prefix + input.sourceCode()
                            ├─ c. cache.getOrCompile(body, shell)
                            ├─ d. boundContext = ContextHydrator.hydrate(input, cachedScript.getClass())
                            ├─ e. binding.setVariable(...)
                            ├─ f. run script
                            └─ g. output = ContextHydrator.dehydrate(bindingMap)
```

[COMPUTED, 置信度 HIGH] 关键点：

- (2) 二次 Feign 拉 ObjectType 是同步流程；若上游 metadata 端能把 attributes 内联到 `objectTypeCodes[*]`（见 §4.4 备选方案），可直接去掉二次拉。
- (3) `ExecutionInput` 加一个 final 字段；DTO 改动小，但向下传递契约清晰。
- (b) 拼 prefix 是端到端的关键；§4.2 给出 `DomainTypePrefixGenerator` 的语义。

### 4.2 DomainTypePrefixGenerator

替换 `DomainTypePrefix`（保留壳做兼容，已标 `@Deprecated`）：

```java
package com.orule.rule.execution.execution.java;

import com.orule.rule.execution.execution.java.metadata.ResolvedObjectType;

import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;
import java.util.stream.Collectors;

/**
 * Renders ObjectType metadata into a Groovy script prefix (RFC-0045 §4.2).
 *
 * <p>Order:
 * <ol>
 *   <li>{@code kind=ENUM} declarations, sorted by {@code programCode}.</li>
 *   <li>{@code kind=CLASS} declarations in <b>topological order</b>:
 *       attributes referencing another ObjectType are emitted after the
 *       referenced type. Cycle breaks by {@code programCode} lexicographic
 *       order (RFC-0045 §8 风险栏).</li>
 * </ol>
 *
 * <p>Nullability: returns empty string when input is null/empty.
 */
public final class DomainTypePrefixGenerator {

    private DomainTypePrefixGenerator() {}

    public static String render(List<ResolvedObjectType> objectTypes) {
        if (objectTypes == null || objectTypes.isEmpty()) {
            return "";
        }
        String enums = objectTypes.stream()
            .filter(o -> "ENUM".equals(o.kind()))
            .sorted(Comparator.comparing(ResolvedObjectType::programCode))
            .map(DomainTypePrefixGenerator::renderEnum)
            .collect(Collectors.joining("\n\n"));

        List<ResolvedObjectType> classes = objectTypes.stream()
            .filter(o -> "CLASS".equals(o.kind()))
            .sorted(Comparator.comparing(ResolvedObjectType::programCode))
            .collect(Collectors.toCollection(ArrayList::new));
        topologicalSort(classes);

        String bodies = classes.stream()
            .map(DomainTypePrefixGenerator::renderClass)
            .collect(Collectors.joining("\n\n"));

        return (enums.isBlank() ? "" : enums + "\n\n") + bodies + "\n";
    }

    static String renderEnum(ResolvedObjectType ot) {
        // ot.enumValues() : List<{code,label,sortOrder}>
        // → "enum X { A, B, C }"
    }

    static String renderClass(ResolvedObjectType ot) {
        // ot.attributes() : List<{programCode, dataType, refCode}>
        // → "class X {\n    String name\n    Integer age\n}"
        // 注：不输出 enum 字段的具体类型 prefix，由 caller 传入 sortOrder=null 默认
    }

    static void topologicalSort(List<ResolvedObjectType> classes) { … }
}
```

约束：

1. 输出文本必须能被 Groovy 4 编译（与 `DomainTypePrefix.CUSTOMER_ORDER` 同结构）。
2. **不**对 `kind=VOID` 的 ObjectType 输出（保留作为 RuleType.returnType=null 标记）。
3. 不重写字符串字面量；输出顺序由 generator 锁。
4. 循环依赖：用程序代码字典序 stable sort，**不**抛异常，记录 `log.warn` 后继续（cruleengine 不允许循环，但极端情况需降级；见 §8）。

### 4.3 RuleExecutionApplicationService 二次 Feign + orule-server 同期补端点（r2a 拍板）

`RuleExecutionApplicationService.execute(...)` 在拿到 `RuleMetadataResponseV2` 后：

### 4.4 RuleMetadataResponse 升级到 v2

**v1 record 退役；v0.2 引入 `RuleMetadataResponseV2`**，破坏性升级：

```java
public record RuleMetadataResponseV2(
        String ruleCode,
        String ruleTypeCode,
        String executorType,
        String sourceCode,
        java.util.List<String> functionTypeCodes,
        java.util.List<String> excludeFunctionTypeCodes,
        String domainCode,                       // 新增（来自 RuleSetType.domain）
        List<String> objectTypeCodes,            // 新增：RuleType.arguments[*].objectTypeCode 去重
        Map<String, Object> extra                // 保留兼容窗口（1 sprint）；crulemgr 必须能在 v0.2 同时下发 v2
) {}
```

迁移策略：

1. `RuleManagermentApiClient.getRuleMetadata(...)` 改返回 `RuleMetadataResponseV2`；原 `RuleMetadataResponse` 删除。
2. `RuleExecutionApplicationService` 与下游 `RuleExecutor` 实现按 v2 编译期 lock-in。
3. `crulemgr` 端：
   - 新增 `GET /api/v1/rules/{ruleCode}` 在 v2 wire format 下发的字段；v1 端点保留 1 sprint 兼容。
   - 新增 `GET /api/v1/object-types/by-program-code?domainCode=&programCode=`（§4.3 已说明）按 v2 同次落地，不走 mock。
4. 测试侧：`RuleExecutionApplicationServiceTest` / `JavaSourceExecutorTest` / `MetadataDrivenPrefixSystemTest` 全部按 v2 编译；旧 v1 期望字段测试删除。

为什么不选 v1 加字段（v2a）或只在 `extra` 塞（v2c）：

- 「保持 v1 record 加字段」会让 `domainCode` / `objectTypeCodes` 长期混在 `extra`，文档无法 lock；其它元数据字段（FunctionType 名单、executorType）后续同样要升 v2，一次到位更省事。[COMPUTED, 置信度 HIGH]
- 「只在 extra 塞」是 RFC-0040 v0.7 留下的逃生通道；本 RFC 把逃生通道收回。[COMPUTED, 置信度 MED]

> **crulemgr 端约束**：v0.2 上线时，`crulemgr` 必须能在同次发布提供 v2 record + 新端点；否则本 RFC 不能落地为单个 release。本 RFC 在 §10 开放问题中保留 crulemgr sprint 对齐事项。

### 4.5 ContextHydrator 通用化（顶层 object slot 递归，list/map 不递归）

```java
public final class ContextHydrator {

    private static final Logger log = LoggerFactory.getLogger(ContextHydrator.class);

    private ContextHydrator() {}

    /**
     * 通用化：按 input.resolvedObjectTypes() 与 context key 匹配，把对应顶层 Map
     * hydrate 成 Groovy POJO。<b>仅递归 hydrate 顶层 object slot</b>；list/map
     * slot 内层不 hydrate（h4a 拍板）。
     *
     * <p>{@code tier} 字符串字段 → enum 的特判不再存在；任何 AttributeType 引用
     * ObjectType(kind=ENUM) 都走 enum 转换（仅作用于顶层 object slot 的属性，
     * 不作用于 list/map 内层）。
     */
    public static Map<String, Object> hydrate(ExecutionInput input, Class<?> scriptClass) {
        if (input == null || input.context() == null || input.context().isEmpty()
                || input.resolvedObjectTypes() == null
                || input.resolvedObjectTypes().isEmpty()) {
            return input.context();
        }
        Map<String, ResolvedObjectType> bySlot = input.resolvedObjectTypes().stream()
            .collect(Collectors.toMap(ResolvedObjectType::slotName, o -> o, (a, b) -> a));
        Map<String, Object> out = new LinkedHashMap<>(input.context());
        for (Map.Entry<String, Object> e : input.context().entrySet()) {
            ResolvedObjectType spec = bySlot.get(e.getKey());
            if (spec == null) {
                continue;                                       // 未知 slot，原样保留
            }
            Class<?> targetClass = findDomainClass(scriptClass, spec.programCode());
            if (targetClass == null) {
                log.warn("Slot {} references programCode={} but script prefix has no such class; skip hydrate",
                        e.getKey(), spec.programCode());
                continue;
            }
            if (e.getValue() instanceof Map<?, ?> m) {
                // 顶层 object slot：递归 hydrate 其属性（enum attr 自动转 enum）
                out.put(e.getKey(), hydrateObject(targetClass, spec, scriptClass, stringMap(m)));
            } else {
                // list / primitive / null：原样保留（h4a 拍板：list 内层不 hydrate）
            }
        }
        return out;
    }

    static Object hydrateObject(Class<?> type, ResolvedObjectType spec, Class<?> scriptClass, Map<String, Object> fields) {
        // 仅当 attribute.dataType=object 且目标是 kind=ENUM 才走 enum 转换。
        // list/map attribute：保留原始 Map / List 形态（不递归 hydrate）。
    }

    /** 用反射读 getter，从 GroovyObject 出 JSON-friendly map。不再 simpleName 特判。 */
    static Object dehydrateValue(Object value) { … }
}
```

变更点：

1. 移除 `CUSTOMER_FIELDS / ORDER_FIELDS`。
2. 移除 `if ("tier".equals(...))`；改为对每个 attribute，若 `dataType=object` 且目标为 `kind=ENUM`，走 enum 转换（仅作用于顶层 object slot 的属性）。
3. `dehydrateValue` 改为遍历 `getClass().getMethods()` 找 `isXxx()` / `getXxx()`，对简单类型（String / Number / Boolean / enum）走原值。
4. 顶层 slot 名 → ResolvedObjectType.slotName 由 metadata 给出（与 RFC-0033 §3.4 ArgumentType.programCode 同值，即业务侧入口变量名）。
5. 写回语义：hydrate 后的 POJO 直接赋值（`order.discount = 30`）仍写回原 map；typed local（`Customer vip = ...`）仍拷贝出，与 RFC-0043 §4.3 一致。

## 8. 风险

| 风险 | 等级 | 缓解 |
| --- | --- | --- |
| ObjectType 拉取慢 / 失败 | 🟠 中-高 | 二次 Feign 走 Resilience4j 默认 2s 超时 + 重试 1 次；失败降级到「无 prefix」路径，依赖 RFC-0043 §4.3 写回语义继续工作 |
| 规则代码中 `customer` 不在 metadata 顶层 | 🟡 中 | hydrate 跳过未知 slot；prefix 仍生成（执行器编译通过）；规则报错 → EVAL_FAILED |
| ObjectType 循环依赖 | 🟡 中 | topological sort 失败时按 programCode 字典序兜底；log.warn 留下诊断；不抛异常 |
| ObjectType 改名 → 旧规则缓存的 prefix 失效 | 🟠 中-高 | `GroovyClassCache` 按 SHA256 缓存；改名后规则 hash 变，自动重编 |
| `@Deprecated` 删除路径遗漏调用方 | 🟢 低 | v0.2 强制清理（grep `DomainTypePrefix`） |
| `extra` 字段重复滥用 | 🟢 低 | 上游若需再带 ObjectType 用顶层字段；本 RFC 文档禁止 |
| RFC-0033 §3.7 不变式 #1 漂移 | 🟠 中-高 | metadata 写入时已断言；执行器不重复校验；启动期 `MetadataIntegrityChecker`（RFC-0033 §3.7）兜底 |
| hydrate 后 `customer.tier == CustomerTier.VIP` 仍 false | 🟡 中 | 与 RFC-0043 §4.5 实施顺序一致：先 enum 注入，再 attr→enum 自动转换；A0 转为 metadata-driven 通过即可 |
