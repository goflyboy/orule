# RFC-0041: 系统级测试（System-Level Test） — 真实 HTTP 服务 + Java 执行器

> **状态**：DRAFT（与代码同步刷新） · **优先级**：P1 · **预计工作量**：0.5d（实现 + RFC）
> **关联 RFC**：[RFC-0040 规则执行服务](RFC-0040-规则执行服务.md)、[RFC-0020 Groovy 沙箱 + 单条规则执行器](RFC-0020-Groovy沙箱单条规则执行器.md)、[RFC-0027 可观测性](RFC-0027-可观测性日志TraceActuator.md)、[RFC-0028 端到端集成测试](RFC-0028-端到端集成测试MVP验收.md)
>
> **v0.1 范围**：补齐 RFC-0040 §3.5 缺失的两块：
> 1. **端到端系统测试**：用 `@SpringBootTest(webEnvironment = RANDOM_PORT)` 起一个真实 HTTP 服务，用 `RestClient`（或 `TestRestTemplate`）作为外部调用方（"CustomerService"）发起请求；除 `RuleManagermentApiClient`（Feign 上游契约）外，其余 Bean 全部真实装配（特别是 `JavaSourceExecutor`）。
> 2. **同步单规则执行日志写入**：当前 `RuleExecutionApplicationService` 不写 `execution_log`；本 RFC 在同步路径上补齐 PENDING → RUNNING → SUCCESS / FAILED 的状态机迁移，并新增 `GET /api/v1/rule-executions/{taskId}/logs` 端点，使同步任务也可被事后审计。

## 2. 动机

RFC-0040 §3.5 落地后，单规则同步路径与 RuleSet 异步路径都已有完整 Controller / Service，但：

1. **同步路径没有审计落库**：CustomerService 等上游业务调用 `POST /api/v1/rule-executions` 后，结果只在响应体里，不留 `execution_log` 行；事后排障只能依赖业务方日志。这与 RFC-0040 §14.2（execution_log 必须覆盖所有执行）和 RFC-0027 §3（可观测性要求）冲突。
2. **没有真实 HTTP 端到端测试**：现有测试要么是 `MockMvc` 单元测（`RuleExecutionControllerTest` / `RuleSetExecutionControllerTest`），要么是 Service 单元测（`RuleExecutorServiceTest`），执行器要么 mock 要么只在 `GroovyClassCache` 层面验证；没有"起完整服务 → 用 HTTP 客户端 → 执行器真实跑 → 验证结果 + 日志"的覆盖。RFC-0028 §3 描述的 E2E 集成测试尚未落地。
3. **CustomerService 视角缺失**：业务方关心的是"我 POST 一条规则，多久后能拿到结果、日志能不能查、错误码怎么映射"。MockMvc 测试无法验证 `TenantInterceptor` 在真实 Servlet 容器上的行为，也无法验证 Tomcat 线程切换对 `TenantContextHolder`（ThreadLocal）的影响。

## 3. 详细设计

### 3.1 新增 GET 端点（同步路径补齐）

```text
GET /api/v1/rule-executions/{taskId}/logs
```

- **契约**：复用 `ExecutionLogApplicationService.findByTaskId(taskId)`，返回 `ExecutionLogDetail`（与 RuleSet 路径同形）。
- **错误码**：未找到 → 404 `TASK_NOT_FOUND`（沿用 §16.6）。
- **路径对称性**：

  | 任务类型 | 提交端点 | 日志端点 |
  | --- | --- | --- |
  | 同步单条 | `POST /api/v1/rule-executions` | `GET /api/v1/rule-executions/{taskId}/logs` |
  | 异步规则集 | `POST /api/v1/rule-set-executions` | `GET /api/v1/executions/{taskId}/logs` |

  > 注：异步日志路径沿用 RFC-0040 §16.4 `executions/{taskId}/logs`（不带 `rule-set-` 前缀），本 RFC 不改它；只在同步路径上新增对称端点。

### 3.2 同步路径补写 execution_log

修改 `RuleExecutionApplicationService.execute(...)`：

```text
PENDING  →  RUNNING  →  SUCCESS | FAILED
```

- **PENDING 行**：在调用 `executorService.execute(...)` **之前** 同步 `logRepo.save(...)`，`executionType = RULE`、`ruleCode = request.ruleCode()`、`executorType = request.ruleCode() 对应的 RuleMetadataResponse.executorType`（即 metadata 拿到的 SPI route key）。
- **RUNNING 行**：进入 `executorService.execute(...)` 后 `markRunning()` + `logRepo.save(...)`。
- **SUCCESS 行**：执行成功后 `markSuccess(outputContextJson)` + `logRepo.save(...)`。
- **FAILED 行**：捕获 `RuleEvalException` / `RuleRuntimeException` / `RuleNotFoundException` / 其它 `RuntimeException` 后 `markFailed(errorCode, errorMessage)` + `logRepo.save(...)`，**仍向上抛**以便 `GlobalExceptionHandler` 映射 HTTP 响应码。
- **事务边界**：与 RuleSet 异步路径（`RuleSetExecutorServiceImpl`）保持一致——PENDING 写入用 `Propagation.REQUIRES_NEW` 立即可见；后续 RUNNING/SUCCESS/FAILED 用默认事务传播。

> **决策点 [INFERRED, 置信度 HIGH]**：保留对调用方（CustomerService）的同步语义不变——响应体里 `taskId` 仍然由 `UUID.randomUUID()` 生成，调用方不感知是否落库；只在落库失败时打 WARN 日志，不阻断业务响应（与 RuleSet 路径一致，见 `RuleSetExecutorServiceImpl` line 213-218）。

### 3.3 系统测试（systemtest 包）

#### 3.3.1 测试入口

```java
@SpringBootTest(
    webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT,
    properties = {
        "spring.kafka.bootstrap-servers=localhost:0"  // 关闭 Kafka 自动连接
    }
)
@AutoConfigureMockMvc  // 同时启用 MockMvc 备用
@ActiveProfiles("dev")
class CustomerServiceSystemTest { ... }
```

- **RANDOM_PORT**：Spring Boot 启动 Tomcat 在随机端口；`TestRestTemplate`（或 `RestClient`）通过 `@LocalServerPort` 拿端口，对外以 CustomerService 视角发 HTTP。
- **Mock 边界**：只 `@MockBean RuleManagermentApiClient`（Feign 上游）；`JavaSourceExecutor`、`GroovyClassCache`、`RuleExecutorService` 全部走真实 Bean 装配。
- **不 Mock 的**：HTTP 层（Tomcat + DispatcherServlet + HandlerInterceptor）、`TenantInterceptor`、`RateLimiter`（默认 100/s，测试负载触发不到）、`ExecutionLogRepository`（真实 H2 + Flyway 迁移）。

#### 3.3.2 用例清单

| # | 场景 | 端点 | 期望 |
| --- | --- | --- | --- |
| 1 | 同步单规则 happy path | `POST /api/v1/rule-executions` | HTTP 200, `success=true`, `outputContext.result=42`；随后 `GET /api/v1/rule-executions/{taskId}/logs` 查到 `RULE / SUCCESS / executor_type=java-source` |
| 2 | 同步单规则 eval-fail | `POST /api/v1/rule-executions` | HTTP 200, `success=false`, `errorCode=EVAL_FAILED`；日志 `FAILED` + `errorCode=EVAL_FAILED` |
| 3 | 同步单规则 runtime-error | `POST /api/v1/rule-executions` | HTTP 200, `success=false`, `errorCode=RUNTIME_ERROR`；日志 `FAILED` + `errorCode=RUNTIME_ERROR` |
| 4 | 同步 missing tenant | `POST /api/v1/rule-executions` 无 `X-Tenant-Id` | HTTP 400 `MISSING_TENANT_HEADER` |
| 5 | RuleSet 提交 + 轮询 + 日志 | `POST /api/v1/rule-set-executions` → 轮询 + `GET /executions/{taskId}/logs` | 终态 `SUCCESS`，`totalCount=1`, `successCount=1`, `failedCount=0` |
| 6 | RuleSet 单条规则失败（PARTIAL_SUCCESS） | RuleSet 提交规则源里塞编译失败 | 终态 `FAILED`（当前 v0.7 placeholder 让 `successCount=0, failedCount=1` ⇒ FAILED；不是 PARTIAL_SUCCESS） |
| 7 | 未知 taskId | `GET /api/v1/rule-executions/{unknown}/logs` | HTTP 404 `TASK_NOT_FOUND` |

> **决策点 [GUESS, 置信度 LOW]**：用例 #6 的"PARTIAL_SUCCESS"路径受 v0.7 placeholder 限制（`RuleSetExecutorServiceImpl` 把 `ruleSetCode` 当作单条规则运行）。等 RFC-0021 落地后会有真正的多规则集合，本 RFC 仅记录这个 gap，不在本 RFC 范围内修复。

#### 3.3.3 测试 fixture 复用

| 来源 | 复用对象 |
| --- | --- |
| `RuleMetadataResponse` | 直接构造（Feign 返回值） |
| `RuleManagermentApiClient` (MockBean) | `when(...).thenReturn(...)` |
| `JavaSourceExecutor` (真实) | SPI 注册于 `META-INF/services` |
| `ExecutionLogRepository` (真实) | 测试结束后通过 `@Transactional` 自动回滚，或 `@DirtiesContext` 清理 |

> **决策点 [INFERRED, 置信度 HIGH]**：系统测试**不需要** `@Transactional` 自动回滚——因为 `RuleExecutorService.execute(...)` 把 `Future.get(timeout)` 抛出的异常穿透事务边界，且 `@Transactional` 只覆盖 `@Test` 方法体；worker 线程已经脱离了事务。改用 `@AfterEach` 显式 `logRepo.deleteAll()` 或 `repository.deleteAllInBatch()` 清理。

## 5. API 变更摘要

### 5.1 新增端点

```http
GET /api/v1/rule-executions/{taskId}/logs
```

Response 200（与 RuleSet 日志同形 `ExecutionLogDetail`）：

```json
{
  "taskId": "a1b2c3d4-...",
  "executionType": "RULE",
  "ruleCode": "ORDER_VIP_DISCOUNT",
  "ruleSetCode": null,
  "executorType": "java-source",
  "status": "SUCCESS",
  "inputContext": {"x": 1},
  "outputContext": {"result": 42},
  "totalCount": null,
  "successCount": null,
  "failedCount": null,
  "errorCode": null,
  "errorMessage": null,
  "perRuleExecution": [],
```

沿用 RFC-0040 §16.6。

## 6. 兼容性

- **API**：新增端点，不破坏既有 `POST /api/v1/rule-executions` 契约；同步响应体不变。
- **数据库**：无 schema 变更。
- **行为**：同步路径从"无日志"变成"有日志"。如果上游业务假设"调用失败时数据库不会写入新行"，需要通知；但 RFC-0040 §14.2 已经声明"execution_log 必须覆盖所有执行"，本次落地反而是**收敛**到一个长期承诺。
- **事务**：执行日志写入失败时打 WARN，不阻断业务响应（与 RuleSet 异步路径一致）。

## 8. 风险

| 风险 | 缓解 |
| --- | --- |
| `@RateLimiter` 在高频测试下触发限流 | 默认 100/s；测试负载 ≤ 10 用例，不触发 |
| 同步路径上写日志可能引入新的事务问题 | 与 RuleSet 异步路径使用相同事务模型（`REQUIRES_NEW` for PENDING） |
| Tomcat 真实 HTTP 容器行为与 MockMvc 不同 | 正是本 RFC 要验证的目标 |
| `JavaSourceExecutor` 真实跑需要 Groovy 编译时间 | 测试设置较短超时（30s default），不构成风险 |
| `KafkaEventPublisher` 在 dev profile 默认连 `localhost:9092`，测试机可能没有 broker | 用 `properties = "spring.kafka.bootstrap-servers=localhost:0"` 禁用；或 `@MockBean KafkaEventPublisher`（仅系统测试） |
